## 阻塞问题

### 1. 福利 CTA 没有执行其宣称的动作，且把不同任务错误地导向 BTC 现货

`mobile/android/app/src/main/kotlin/click/cowa/linbit/feature/more/WelfareScreen.kt:90-100,105-118`

- 后端对未报名用户返回 `cta=enroll`，对已经开始活动但未完成者返回 `cta=continue`。现在 UI 文案分别显示「立即参与」「继续任务」，点击后却都执行 `onTrade(false, "BTCUSDT")`，没有报名或任务详情流程。
- 服务端实际已有 `POST /rewards/newcomer/enroll`；任务类型也包括绑定邮箱/手机、首次充值并划转合约、合约交易量。硬编码 BTC 现货尤其不符合首次充值/合约任务，用户点了「立即参与」也不会真正报名。
- 当前 PR 文案「无领取端点的 CTA 明确提示即将开放」不准确：报名端点存在，`GET /rewards/newcomer` 和任务领取端点也已由 growth 服务提供，但两份 OpenAPI 尚未完整列出这些路径。请协调补齐契约后接入真实的报名、任务详情和可领取动作；如果只是本轮不做，应明确显示「报名/领取功能尚未接入」，不能保留「立即参与/继续任务」并跳往无关交易页。

### 2. 通知单条已读失败会整包回滚，覆盖较新的状态/账号数据

`mobile/android/app/src/main/kotlin/click/cowa/linbit/feature/more/NotificationsScreen.kt:79-90`

- `markRead` 先把整个 `NotificationState` 保存为 `old`，请求失败后 `_state.value = old`。
- 用户快速点击两条未读时，后发成功的那条也会随先发失败而被改回未读；分页加载或「全部已读」的状态同样可能被旧快照覆盖。
- `sessionVersion` 复位之后，旧账号在飞的已读请求失败仍可把旧账号的通知列表和未读计数写回来。应只回滚对应的 item、未读总数及相应 kind 计数，并基于当前状态计算；同时捕获 session version，响应必须仍属于当前账号才可以写状态。

建议对「连续标记两条、第一条失败第二条成功」与「切账号后旧请求失败」补测试。`NotificationBadgeViewModel.kt:23-35` 也应在异步未读数返回时校验 session，避免旧账号角标晚到。
